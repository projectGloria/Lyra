# Bug and performance audit

Date: 2026-09-29. Scope: current JavaScript frontend, Rust backend, native bridge, scanning/cache/watcher paths, artwork editing, and playback state.

## Fix status

All 11 reproduced bugs and all three performance findings have been addressed in the application source. The scan/edit lost-update risk also has a shared revision guard and a deterministic retry test. This document preserves the original reproductions below as a record of what was found; the fixes are covered by the normal JavaScript and Rust suites. Latest validation: **42 JavaScript tests and 31 Rust tests pass**; Rust formatting passes; the Windows release binary and NSIS installer build successfully. A 50,000-track synthetic check now creates an approximately **8.1 KiB visible queue window in 0.2 ms**, while a closed queue does no rendering. Native debug benchmarks measured one-file refreshes at **864 ms for 5,000 root tracks** and **404 ms for 5,000 tracks across 100 folders**; 3,000-track artwork lookup fell from 1,241 ms to **46 ms**. These local fixture timings are workload examples, not release-build predictions.

## Summary

Found **11 reproduced correctness bugs**, including **two data-loss bugs**, plus **three measured performance issues**. One additional concurrency risk is identified by source inspection. Fix the two data-loss bugs first.

At the time of the audit, the existing suites had **33 JavaScript tests and 24 Rust tests**. New probes exposed **eight JavaScript failures and three Rust failures**; one JavaScript control test passed. Those pre-fix counts and failures are retained here to document the original findings.

JavaScript reproductions execute actual functions in Node VM contexts with explicit UI/native stubs. Native reproductions compile the repository modules and use disposable temporary fixtures. No personal music files were used. No live WebView playback, GPU profiling, or installer validation was performed.

## High priority: data loss

### B1. Startup cleanup permanently deletes unrelated user files

**Location:** [util.rs:278](../src-tauri/src/util.rs:278), called from [scan.rs:111](../src-tauri/src/scan.rs:111).

On the first valid scan in a process, maintenance scans the music root. It deletes any file older than five minutes whose name contains `.tmp-`, without checking that Lyra created it. A legitimate `mix.tmp-final.mp3` matches. Deletion uses `remove_file`, bypassing the Recycle Bin.

**Reproduced:** created that filename, set its modification time ten minutes back, invoked cleanup, and observed the file disappear.

**Fix:** restrict cleanup to exact Lyra-owned temporary naming patterns and validated numeric suffixes. Never classify arbitrary music filenames as application temporary files. Scope cleanup to known managed targets.

### B2. A failed tag save still deletes the original cover

**Location:** [scan.rs:878](../src-tauri/src/scan.rs:878), [scan.rs:965](../src-tauri/src/scan.rs:965).

Changing/removing artwork deletes `Song.jpg` before `save_to_path` attempts to write `Song.mp3`. If the write fails, the command returns an error but the original image is already permanently gone.

**Reproduced on Windows:** held the audio file with read sharing only, requested artwork removal, and observed both a failed save and a deleted sidecar.

**Fix:** stage changes and preserve the original cover until the audio write succeeds; restore it on failure. Treat the operation as a transaction across both files.

## Medium priority: playback and editing

### B3. Renamed track IDs disagree with the backend

**Location:** [renderer.js:1869](../src/renderer.js:1869), [util.rs:55](../src-tauri/src/util.rs:55).

The renderer hashes a lowercase, slash-normalized path and retains 12 hex characters. Rust hashes the original path and retains 16. For `C:\Music\New\Song.mp3`, the reproduction produces `a2954df69a49` in JavaScript and `47fba1eb4170b7ac` under the Rust contract.

The next scan replaces these temporary IDs, dropping selected IDs and playback history; navigation to a renamed subfolder can also lose its identity. The existing rename regression test repeats the frontend's incorrect algorithm, so it passes.

**Fix:** use the exact backend identity contract, preferably return the remapping from Rust. Test shared input/output vectors across languages.

### B4. Saving metadata replaces the active playback collection

**Location:** [renderer.js:1829](../src/renderer.js:1829).

After saving the current track, the editor calls `setCurrentTrack` with `state.playbackQueue` or `state.selectedTracks`. The actual playback collections are `playbackList` and `basePlaybackList`; browsing another playlist changes `selectedTracks`.

**Reproduced:** playback `[A, B]`, current `A`, browsing `[X]`; saving A changes playback to `[X]`. Shuffle order and the cursor for a queued song can also change.

**Fix:** resume with no replacement collection and preserve the existing queue anchor/history, as the playlist editor already attempts to do.

### B5. A late metadata save restarts the previous song

**Location:** [renderer.js:1826](../src/renderer.js:1826).

The `finally` block restores the captured track unconditionally. If the user closes the modal and presses Next, uses a media key, or switches libraries while a slow save is pending, its completion can undo that newer action. There is also no save-in-progress guard.

**Reproduced:** start saving A, select B, then resolve A's save; current track becomes A again.

**Fix:** capture and verify `playbackRequestId`, track identity, and library identity before restoring playback. Prevent duplicate submissions.

### B6. Native metadata errors bypass the user-facing error message

**Location:** [renderer.js:1811](../src/renderer.js:1811), [renderer.js:2781](../src/renderer.js:2781).

Tauri rejects the promise for a Rust `Err`. The editor has `try/finally` without `catch`; the later `result?.ok` check never runs. Its submit listener does not handle the rejected promise either. The global rejection handler only logs it.

**Reproduced:** an `Access denied` rejection escapes `saveTrackEditor` with no error toast.

**Fix:** catch native failures, display the error, and retain the editor contents for retry.

### B7. Recognized suffix sidecars override newly saved artwork

**Location:** [artwork.rs:90](../src-tauri/src/artwork.rs:90), [scan.rs:885](../src-tauri/src/scan.rs:885).

Artwork lookup recognizes `Song-cover.jpg`, `Song_front.jpg`, and related suffixes. Editing removes an existing sidecar only when its stem exactly equals `Song`. The suffix variant survives and still takes precedence over the newly embedded image.

**Reproduced:** replace artwork for `Song.mp3` with an existing `Song-cover.jpg`; the command succeeds but returns the old sidecar as the displayed artwork. Removal has the same precedence problem.

**Fix:** share artwork resolution rules between reading and editing, and define an explicit replacement/removal policy that preserves originals on failure.

### B8. Playlist rename misses current and queued objects after tag editing

**Location:** [renderer.js:1759](../src/renderer.js:1759), [renderer.js:1892](../src/renderer.js:1892).

`refreshEditedTrack` creates separate merged objects for the library, current track, queue, and playback lists. `refreshEditedPlaylist` later updates only the objects stored inside library folders, relying on those objects being shared.

**Reproduced:** edit a track, then rename its folder; the library track receives the new path while the current track retains `C:\Music\Old\Song.mp3`. Queued/playback copies also remain stale. Resuming can target a nonexistent file; subsequent reconciliation can drop those entries.

**Fix:** remap every playback collection explicitly, or maintain one canonical track object per identity and reconcile all references after edits.

### B9. Cache-busting queries become literal filename characters during rename

**Location:** [tauri-bridge.js:42](../src/tauri-bridge.js:42), [renderer.js:1762](../src/renderer.js:1762), [renderer.js:1858](../src/renderer.js:1858).

Tag refresh adds `?v=...` to artwork URLs. `fromAssetUrl` appends `url.search` to the decoded filesystem path. Renaming a playlist then converts that combined string back to an asset URL, encoding the query as part of the filename.

**Reproduced:** renaming `.../Song.jpg?v=123` produces an asset request for the literal filename `Song.jpg?v=123`, causing artwork to fail until refreshed.

**Fix:** decode the pathname alone. Preserve URL query parameters separately when remapping.

## Lower priority: visible state

### B10. The open queue stays stale when playback consumes an entry

**Location:** [renderer.js:1152](../src/renderer.js:1152), [renderer.js:1570](../src/renderer.js:1570).

`nextTrack` removes an entry from state and updates the player, but neither that path nor `updatePlaybackUi` refreshes the queue panel. An open panel continues showing a consumed entry and the old count. Clicking that stale entry does nothing because it no longer exists in `state.queue`.

**Reproduced:** automatic advancement empties the queue without invoking its renderer.

**Fix:** refresh the visible queue/history panel when playback changes its underlying state.

### B11. A library containing only empty playlists hides those playlists

**Location:** [renderer.js:559](../src/renderer.js:559), [renderer.js:768](../src/renderer.js:768).

Both sidebar and content rendering return an empty-library message whenever `trackCount` is zero. Creating a playlist in an empty library succeeds on disk, but the new playlist cannot be opened, renamed, or deleted through these views until an audio file is added.

**Reproduced:** a valid zero-track library containing `New Playlist` renders only the no-audio message.

**Fix:** distinguish an empty collection from an absent library; render existing playlist folders even when they have no tracks.

## Performance findings

### P1. Queue rendering creates every row, including when the panel is closed

**Location:** [renderer.js:1027](../src/renderer.js:1027), [renderer.js:2085](../src/renderer.js:2085).

Adding a playlist calls `renderQueuePanel` immediately. It builds HTML for the entire queue, unlike the virtualized main track list.

Synthetic Node measurements, median of three measured runs after warm-up:

| Queued tracks | HTML generation | HTML size | Library normalization |
|---:|---:|---:|---:|
| 1,000 | 6.9 ms | 0.54 MiB | 2.2 ms |
| 10,000 | 65.0 ms | 5.42 MiB | 21.8 ms |
| 50,000 | 329.0 ms | 27.38 MiB | 114.8 ms |

These measure actual renderer functions with DOM stubs and simplified icons. Browser parsing, layout, images, IPC, and native URL conversion are **excluded**, so these are not end-to-end UI timings.

**Fix:** virtualize the queue; defer closed-panel rendering. Avoid rebuilding all track indexes for changes confined to one track or playlist.

### P2. A one-file refresh still rebuilds and writes the whole library

**Location:** [scan.rs:109](../src-tauri/src/scan.rs:109), [scan.rs:191](../src-tauri/src/scan.rs:191), [scan.rs:412](../src-tauri/src/scan.rs:412), [cache.rs:141](../src-tauri/src/cache.rs:141), [tauri-bridge.js:50](../src/tauri-bridge.js:50).

Incremental scanning loads the full track cache and snapshot, makes jobs for all tracks, reconstructs all collections, writes both complete JSON files with synchronization, and returns the full library for frontend URL mapping/indexing. If all tracks share one folder, changing one file revalidates that whole folder.

Native synthetic measurements with valid tiny WAV fixtures, warm cache, **debug build**, no Tauri window:

| Existing tracks | Playlist subfolders | Warm full scan | Add one file |
|---:|---:|---:|---:|
| 1,000 | 0; all in root | 675 ms | 719 ms |
| 5,000 | 0; all in root | 4,596 ms | 5,148 ms |
| 5,000 | 100 | 1,576 ms | 1,315 ms |

The 5,000-track/100-folder update rewrites approximately **5.85 MB** across the two cache files for a single added song. These are workload examples, not release-build predictions; an earlier flat-library run took 4.2 seconds instead of 5.1 seconds for the same operation.

**Fix:** track dirty records/folders, commit deltas, and avoid serializing unchanged data. Keep a reusable in-memory index or use transactional storage. Send frontend changes instead of returning the entire library for every event.

### P3. Cached artwork lookup remains quadratic in folders with many images

**Location:** [artwork.rs:90](../src-tauri/src/artwork.rs:90).

The directory cache now shares an `Arc`, removing the previous vector-cloning cost. Each track still linearly searches all images and repeatedly allocates lowercase stems; suffix matching adds more allocation. With one image per track, the work is O(tracks × images).

**Measured after warming the directory cache:** 1,000 matching tracks/images took **107 ms**; 3,000 took **1,241 ms** in the debug build. Directory reads and fixture creation are outside these measurements.

**Fix:** build a lowercase-stem-to-path map once per directory, preserving deterministic tie-breaking and suffix precedence.

## Additional concurrency risk: source verified, not reproduced

Scans hold `scan_lock` ([main.rs:133](../src-tauri/src/main.rs:133)); metadata editing holds a different `playlist_lock` ([main.rs:262](../src-tauri/src/main.rs:262)). Both independently load and replace the same track cache and library snapshot ([scan.rs:991](../src-tauri/src/scan.rs:991)). An older scan can commit after an edit and overwrite its cached metadata; the reverse ordering can overwrite a newer scan's snapshot. Atomic file replacement prevents partial JSON, but does not prevent stale writers.

Use a shared commit version/transaction or synchronization around cache ownership. Add a deterministic concurrent scan/edit test before changing the locking; restoring a full-scan lock around every editor action would reintroduce long waits.
