# UX and interface

The interface is well built for a hand-rolled one: real focus-visible styling throughout, a `prefers-reduced-motion` block, `aria-live` on the scan summary and toast, a working focus trap with `inert` on the modals, caret preservation across search re-renders, and comments that show the interaction problems were thought about rather than guessed at. The findings below are specific gaps, not a general complaint.

### [Medium] Arrow keys are globally hijacked for volume and seek

**Where:** [src/renderer.js:2649](src/renderer.js:2649), [src/renderer.js:2641](src/renderer.js:2641)
**Trigger:** Press Up/Down or Left/Right with focus anywhere that isn't a text input, a modal, or a track row — the library sidebar, a playlist card, a `<button>`, or `document.body` after clicking empty space.
**Detail:** The handler's guard excludes modals, Alt, and editable fields, but nothing else:

```js
if (!activeModal && !event.altKey && !document.activeElement?.matches('input, textarea, select, [contenteditable="true"]')) {
  ...
  if (['ArrowUp', 'ArrowDown'].includes(event.key)) {
    event.preventDefault(); setVolume(audio.volume + (event.key === 'ArrowUp' ? 0.05 : -0.05), true); return;
  }
```

Because it calls `preventDefault()`, native scrolling is suppressed as well as replaced.
**Impact:** A keyboard user cannot scroll the library sidebar, the home playlist grid or the now-playing panel with arrow keys — the volume changes instead, silently. This is the most likely keyboard action in a list-heavy app and it does something unrelated and destructive to the listening experience.
**Fix:** Require an explicit modifier for the global transport shortcuts, or scope the volume/seek fallback to when focus is on the player dock / `document.body`, letting scrollable regions keep native arrow behaviour.

### [Medium] Unplayable formats are indistinguishable from playable ones until you press play

**Where:** [src-tauri/src/util.rs:9](src-tauri/src/util.rs:9) — see [01-bugs.md](01-bugs.md) for the mechanism
**Impact:** From the user's side: a track with full metadata and artwork sits in a playlist, and clicking it produces `Playback error: <title> — unsupported or unreadable audio` followed by an automatic skip two seconds later. Nothing indicates the file is fine and the app simply cannot decode that format. After five in a row playback stops with a message that suggests the files are corrupt.
**Fix:** Mark known-undecodable extensions in the row (dimmed, with a "format not supported" title) so the limitation is visible before the click, and change the five-in-a-row message to name the format when that's the cause.

### [Medium] Mutating actions appear dead during a scan

**Where:** [src/renderer.js:1980](src/renderer.js:1980) — see [01-bugs.md](01-bugs.md) for the lock mechanism
**Impact:** "Create playlist", "Save changes" and "Delete playlist" block on `scan_lock` for the duration of a scan. `createPlaylist` awaits with no pending state, no disabled button and no spinner, so on a first run over a large library the + button does nothing visible for minutes. A user will click it several times; every click queues another folder, and they all appear at once when the scan finishes.
**Fix:** Disable the mutating controls while `state.scanning` is true with a tooltip explaining why, or give the button a pending state on click.

### [Low] Search shows eight songs but Play plays all of them

**Where:** [src/renderer.js:709](src/renderer.js:709), [src/renderer.js:736](src/renderer.js:736)
**Detail:** `renderSearchView` assigns the complete match set to `state.selectedTracks`, then renders only the first eight:

```js
state.selectedTracks = tracks;                       // all matches
...
${tracks.slice(0, 8).map(...)}                       // eight rows
```

There is no "show all results" affordance, and the heading count (`N matching results`) sums songs + artists + albums + playlists, so it doesn't match the eight rows either.
**Impact:** Pressing Space or the transport play button from a search view starts a queue of tracks the user cannot see or scroll. For a query matching 400 songs, that is a 400-track queue built from an eight-row list.
**Fix:** Either cap `state.selectedTracks` to what is rendered, or add a "See all N songs" link that opens a full list view.

### [Low] Renaming a playlist folder in Explorer appears to do nothing

**Where:** [src-tauri/src/scan.rs:346](src-tauri/src/scan.rs:346)
**Detail:** The sidecar's stored name wins over the folder basename for display. A user who renames the folder on disk — a reasonable thing to do in an app whose pitch is "every folder with audio becomes a playlist" — sees no change in Lyra after the rescan.
**Impact:** The folder-is-the-database promise leaks: names are the one attribute that lives in a sidecar rather than in the filesystem, and nothing in the UI says so. Combined with the revert bug in [01-bugs.md](01-bugs.md), the user's rename can also be silently undone later.
**Fix:** When the sidecar name matches neither the folder basename nor a previously recorded basename, prefer the folder. Or state in the editor that the title renames the folder.

### [Low] Queue tabs expose a tablist role without the state that makes it usable

**Where:** [src/index.html:154](src/index.html:154), [src/renderer.js:1036](src/renderer.js:1036)
**Detail:** The queue panel's tabs carry `role="tablist"`/`role="tab"` but never set `aria-selected`, have no `aria-controls` pointing at `#queueList`, and the list itself has no `role="tabpanel"`. `renderQueuePanel` syncs only a CSS class:

```js
document.querySelectorAll('[data-action="queue-tab"]').forEach((button) => button.classList.toggle('active', ...));
```

The library filter pills nearby do this correctly ([renderer.js:568](src/renderer.js:568) sets `aria-selected`), so this is an inconsistency rather than an unknown pattern.
**Impact:** A screen reader announces both tabs identically with no selected state, so "Up next" vs "History" is indistinguishable without sighted context.
**Fix:** Set `aria-selected` in the same loop and add `aria-controls="queueList"` plus `role="tabpanel"`.

### [Low] The context menu declares `role="menu"` but has no menu keyboard model

**Where:** [src/index.html:170](src/index.html:170), [src/renderer.js:1894](src/renderer.js:1894)
**Detail:** The six items are `<button role="menuitem">`. `showTrackContextMenu` focuses the first item and Escape closes it, but there is no arrow-key roving focus, no `aria-activedescendant`, and Tab moves focus out of the menu into the page behind it while the menu stays open.
**Impact:** Assistive tech announces a menu and then behaves like a plain button group; keyboard users can tab out of an open menu and leave it floating over the content.
**Fix:** Either implement arrow-key navigation and a focus trap, or drop the ARIA menu roles and let it be a group of buttons, which matches the actual behaviour.

### [Low] Scan progress percentages are stage-weighted, not work-weighted

**Where:** [src-tauri/src/scan.rs:72](src-tauri/src/scan.rs:72) and the `emit` calls through to line 415
**Detail:** The stage boundaries are hardcoded: validate 2%, folders 18%, index 28%, metadata 28→90%, artwork 91%, finalize 94%, complete 100%. Discovery is a full breadth-first walk of the tree that emits nothing between 2% and 18%.
**Impact:** On a deep library on a slow or network drive, the bar sits at 2% through the longest phase and then races through the rest. The progress detail text does update, so it isn't a dead UI — but the percentage misleads.
**Fix:** Emit a folder count during the walk and drive the early segment off it, even without a known total.
