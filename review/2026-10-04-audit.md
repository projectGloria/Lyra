## Reproduced bugs

### B1. Playlist artwork changes commit before the metadata save succeeds

Locations: [playlist.rs:287](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/playlist.rs:287>), [playlist.rs:308](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/playlist.rs:308>), [playlist.rs:69](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/playlist.rs:69>), [playlist.rs:83](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/playlist.rs:83>).

`edit_playlist` removes or replaces `.lyra-cover.*` before writing `.lyra-playlist.json`. Removal uses permanent `remove_file`. If the metadata write fails, the function returns an error without restoring the old cover. Replacement also removes covers with other extensions before metadata commits.

**Reproduction:** create a playlist and its managed JPG cover; hold the metadata file open on Windows with read sharing only; request cover removal. The command returns `Access is denied (os error 5)`, but `.lyra-cover.jpg` is gone. The untouched metadata still references that deleted file. This can lose the only in-folder copy of a cover. The originally selected external image is not deleted.

**Recommended direction:** stage both artwork and metadata and retain rollback copies until the entire save succeeds. The existing cover test only checks an unreadable replacement source, so it misses this later failure.

### B2. A saved-position seek can be applied to the next song

Locations: [renderer.js:1554](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:1554>), [renderer.js:1914](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:1914>), [renderer.js:2081](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:2081>), [renderer.js:3157](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:3157>).

Startup/session restoration and editor playback restoration set the global `restorePosition`. The next `loadedmetadata` event consumes it without checking which playback request or track owns it. Ordinary `setCurrentTrack` does not clear it.

**Reproduction:** pending restore for A at 42 seconds; select B before metadata loads; dispatch B's metadata handler with a 120-second duration. B starts at **42 seconds** instead of zero. Slow disk reads make the user-facing race easier to hit.

**Recommended direction:** associate each pending seek with the track and playback request, and discard it when another selection supersedes that request.

### B3. Previous through queued playback loses the playlist cursor

Locations: [renderer.js:1649](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:1649>), [renderer.js:1554](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:1554>), [renderer.js:1229](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:1229>).

History records track IDs but not their playlist cursor or whether playback came from the temporary queue. `previousTrack` guesses queue origin from membership in `playbackList`. This cannot recover the anchor that existed when a queued song played.

**Reproduction:** playlist `[A, B, C, D]`, current B, queue X. Advance to X, then C. Previous correctly selects X, but Next selects **D**, skipping C. In another probe where the queued song was A, Previous selected A and Next replayed B. Queue membership in the playlist changes the failure mode.

**Recommended direction:** preserve playback origin and anchor in history, so moving back through consumed queue entries retains a coherent forward sequence.

### B4. Removing a playlist cover can bring back a deleted artwork path

Locations: [artwork.rs:30](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/artwork.rs:30>), [artwork.rs:60](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/artwork.rs:60>), [playlist.rs:287](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/playlist.rs:287>), [scan.rs:387](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/scan.rs:387>).

Artwork-directory listings survive incremental scans. Native track editing explicitly invalidates the directory index; playlist-cover editing does not. Its managed image changes are also marked as local writes, allowing the watcher to suppress the very image events that would invalidate those listings.

**Reproduction:** playlist with an audio file and managed JPG cover; scan it to populate the artwork index; replace the cover with PNG and then remove it; add an audio file and run an audio-only incremental refresh. The resulting playlist artwork is the old `.lyra-cover.jpg` path, even though that file no longer exists. A full rescan clears this stale index.

**Recommended direction:** invalidate the containing artwork directory after successful playlist-cover changes, including removal.

### B5. Search rows can all be removed from the keyboard tab order

Locations: [renderer.js:752](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:752>), [renderer.js:1030](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:1030>), [renderer.js:874](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:874>).

Track rows receive `tabindex="0"` only for `focusedTrackId`, or the first row when that ID is empty. Virtualized playlist setup repairs an out-of-collection ID; search rendering does not.

**Reproduction:** previous focused track A, search results containing only X. X renders with `tabindex="-1"`, and no song row has `tabindex="0"`. Nested buttons remain tabbable, but the row's direct Enter/Space playback interaction is unavailable through normal tab navigation. With larger result sets, the remembered focus can also lie beyond the eight displayed results.

**Recommended direction:** choose a focus ID from the displayed search rows and preserve it only while that row remains displayed.

## Performance

### P1. Show-all search bypasses track virtualization

Location: [renderer.js:778](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:778>).

The main collection uses virtual rows, but search maps every matching track into one HTML string when Show all is enabled. Every subsequent search render rebuilds those rows.

Actual search/row functions, synthetic matches, one warm-up followed by three measured runs:

| Matching tracks | Median HTML generation | Generated HTML | Rows |
|---:|---:|---:|---:|
| 1,000 | 11.3 ms | 0.86 MiB | 1,000 |
| 10,000 | 117.3 ms | 8.69 MiB | 10,000 |
| 50,000 | 555.9 ms | 43.75 MiB | 50,000 |

These measurements exclude browser DOM parsing, layout, image loading, and IPC. Icons/artwork were stubbed. They demonstrate substantial synchronous work, not an end-to-end WebView timing.

**Recommended direction:** reuse virtualization or paginate search songs.

### P2. Incremental scans still scale with the entire library

Locations: [scan.rs:182](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/scan.rs:182>), [scan.rs:231](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/scan.rs:231>), [cache.rs:168](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/cache.rs:168>), [library_delta.rs:31](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/library_delta.rs:31>).

The journal/delta work has improved persistence and IPC. However, one-file refreshes still create jobs for unchanged tracks, clone cached track objects, reconstruct collections, compare the full library, and compute active cache keys. The first mutation of shared cache entries can also clone the full underlying map via `Arc::make_mut`.

Measured with valid tiny WAV files, warmed caches, actual Rust modules, **debug build**, no Tauri window:

| Tracks | Playlist subfolders | Warm full scan | Add one file |
|---:|---:|---:|---:|
| 1,000 | 0; all in root | 343 ms | 126 ms |
| 5,000 | 0; all in root | 2,195 ms | 599 ms |
| 5,000 | 100 | 1,240 ms | 273 ms |

These are single-run workload samples, not release-build predictions. The incremental path is substantially faster than a full scan, but its remaining whole-library work can become noticeable for large collections or repeated imports.

**Recommended direction:** retain unchanged collections/indexes and commit only affected records; measure a release build before choosing the size of a refactor.

### P3. Native tag edits invalidate the renderer's delta baseline

Locations: [scan.rs:1098](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/scan.rs:1098>), [renderer.js:1835](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:1835>), [renderer.js:2368](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src/renderer.js:2368>).

Native metadata editing advances the cached snapshot's `scanned_at`. Its response contains the updated track, and `refreshEditedTrack` applies that track without updating `state.library.scannedAt`. The next incremental refresh is based on the newer native snapshot, so the renderer's baseline check rejects the delta and requests a full scan.

**Reproduced call sequence:** frontend timestamp 100, native post-edit baseline 101; a changed-file refresh calls **incremental → full**. The rejection protects correctness, but costs an extra scan after an ordinary edit. The playback/storage benefit of deltas is therefore partially lost during tag-edit workflows.

**Recommended direction:** return and apply the committed snapshot revision alongside the edited track, or provide an edit delta with a matching baseline.

## Additional source-level observations

- **Watcher recovery risk, Medium, not reproduced:** [watcher.rs:80](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/watcher.rs:80>) silently drops watcher errors. [watcher.rs:65](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/src/watcher.rs:65>) treats a same-root watch request as already healthy. If an error represents a lost subscription, there is no health state, user notification, full-refresh request, or explicit restart path for that root. Actual behavior after removable/network storage disconnects needs a live Windows test. Continuous filesystem activity can also defer updates indefinitely because debounce has no maximum wait.
- **Security hardening, informational:** [tauri.conf.json:56](<C:/Users/Nihil/Desktop/Github Repos/Lyra/src-tauri/tauri.conf.json:56>) disables CSP. No exploitable script-injection path was established in this review; ordinary metadata output is escaped and native edit/delete boundaries validate library containment. For this personal local app, missing CSP is a hardening gap rather than a demonstrated critical vulnerability. Dependency advisory checks were not performed.
- **Formatting only:** `cargo fmt -- --check` reports differences in `main.rs` and `playlist.rs`. These are not runtime findings and were left unchanged.
